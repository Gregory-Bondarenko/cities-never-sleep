# Архитектура

Документ описывает устройство продукта: слои, контракты данных и правила их изменения. Раздел «Текущее состояние» отражает то, что уже есть в коде; раздел «Целевое состояние» служит ориентиром и меняется только через ADR.

## Слои

```
 Источники            Аналитика (analytics/)                     Артефакты               Витрина (web/)
┌──────────────┐   ┌─────────────────────────────────────┐   ┌──────────────────┐   ┌──────────────────┐
│ Zenodo VNL   │──▶│ sources/   загрузка, манифест        │   │ data/processed/  │   │ только чтение    │
│ Wikidata     │──▶│ process/   обрезка, нормализация     │──▶│ analytics/       │──▶│ JSON / Parquet / │
│ OSM (план)   │──▶│ metrics/   зональная статистика (план)│   │   exports/       │   │ PMTiles          │
│ Black Marble │──▶│ notebooks/ разведочный анализ        │   │ + *.meta.json    │   │                  │
└──────────────┘   └─────────────────────────────────────┘   └──────────────────┘   └──────────────────┘
       raw                     interim                           processed / exports
  (не в git)               (не в git)                           (в git, небольшие)
```

Связи между слоями однонаправленные. Витрина не знает об устройстве аналитики и опирается только на контракты артефактов.

## Хранение данных

| Каталог | Содержимое | В git | Кто пишет |
|---|---|---|---|
| `data/raw/<источник>/` | исходные файлы и `manifest.json` с контрольными суммами | нет | `cns fetch-*` |
| `data/interim/<источник>/` | обрезанные и нормализованные растры | нет | `cns process-*` |
| `data/manual/` | ручные выгрузки (Росстат XLSX) | нет | человек |
| `data/processed/<набор>/` | агрегаты для анализа (Parquet + CSV) | да | `cns` |
| `analytics/exports/` | облегчённые выгрузки для витрины | да | `cns export-*` (план) |

Ограничение на размер артефакта в git: до 10 МБ на файл. Всё, что больше, собирается локально или публикуется отдельным релизным вложением.

## Контракт артефакта

Каждый набор в `data/processed/` и `analytics/exports/` состоит из файла данных и файла `<имя>.meta.json`. Обязательные поля метаданных:

| Поле | Значение |
|---|---|
| `schema_version` | версия схемы набора по SemVer, независимая от версии пакета |
| `source` | источник или список источников |
| `built_at` | дата и время сборки в UTC (ISO 8601) |
| `package_version` | версия пакета `cities-never-sleep`, собравшего набор |
| `n_rows` | число строк |
| `license_note` | лицензия исходных данных |

Правила версии схемы: переименование или удаление столбца повышает MAJOR, новый столбец повышает MINOR, исправление значений без смены структуры повышает PATCH. Витрина проверяет MAJOR при загрузке.

На момент версии 0.1.0 набор `population/ru_cities_population` не содержит `schema_version`, `built_at` и `package_version`; приведение к контракту запланировано в вехе v0.2.0.

## Целевое состояние (v1.0.0)

### Ключ города

Единый идентификатор города `city_id` равен идентификатору Wikidata (`Q…`). ОКТМО хранится как атрибут и проходит нормализацию: 11 знаков, только цифры; для городов федерального значения допускается 8 знаков. Выбор `city_id` вместо ОКТМО обоснован тем, что ОКТМО в Wikidata заполнен не у всех городов и встречаются ошибочные значения.

### Наборы данных

| Набор | Зерно | Ключ | Основные поля |
|---|---|---|---|
| `cities` | город | `city_id` | `name`, `oktmo`, `region`, `lat`, `lon`, `geometry_source` |
| `city_population` | город × год | `city_id`, `year` | `population`, `source`, `is_census` |
| `city_lights` | город × год | `city_id`, `year` | `sol` (сумма излучения), `lit_area_km2`, `mean_radiance`, `n_valid_months`, `flags` |
| `city_trends` | город | `city_id` | наклон тренда, значимость, класс динамики, сравнение с населением |

Состав полей уточняется в вехах v0.2.0–v0.4.0, финальная схема фиксируется в ADR.

### Конвейер

```
fetch-*  →  process-*  →  build-marts  →  export-web
 raw         interim       processed        exports
```

Каждая стадия запускается отдельно и идемпотентна. Полный прогон описывается в `Makefile`; при росте числа стадий допускается переход на DuckDB с dbt, решение оформляется отдельным ADR.

## Качество

- `ruff` и `pytest` на каждый PR, без обращений к сети.
- Отдельный workflow `network` проверяет доступность Zenodo и Wikidata по расписанию и вручную; в обязательные проверки PR он не входит.
- Проверки данных (уникальность ключей, формат ОКТМО, диапазоны значений) выполняются функциями в `analytics/citiesneversleep/validate/` и покрываются тестами на синтетических данных.
