# ADR-0003. Версионирование, ветки и релизы

- Статус: Принято
- Дата: 2026-10-30

## Контекст

Проект ведётся как продукт: изменения должны быть прослеживаемыми, версии понятными, история `main` чистой.

## Решение

1. **Версия продукта** по SemVer: поле `version` в `pyproject.toml` (формат PEP 440, например `0.2.0.dev0`) и `__version__` в `analytics/citiesneversleep/__init__.py` (отображение `0.2.0-dev`).
2. **До v1.0.0** несовместимые изменения CLI или схем артефактов повышают MINOR, остальное повышает PATCH.
3. **Версия схемы артефакта** ведётся отдельно в `*.meta.json` (см. [architecture.md](../architecture.md)).
4. **Ветки**: `main` всегда рабочая; работа в ветках `<тип>/<кратко>`, слияние только через PR.
5. **Слияние**: squash merge, заголовок PR по Conventional Commits становится сообщением коммита в `main`. Ветка удаляется после слияния.
6. **Релиз**: перенос записей из `[Unreleased]` в раздел версии в `CHANGELOG.md` отдельным PR `chore(release): vX.Y.Z`, затем тег `vX.Y.Z` на коммите слияния и GitHub Release с текстом из журнала.
7. **Вехи**: каждой минорной версии соответствует milestone на GitHub.

## Последствия

- Один PR соответствует одной строке истории `main` и, как правило, одному issue.
- Версия в коде между релизами имеет суффикс `dev`, что исключает путаницу с выпущенными версиями.
- Тег `v0.1.0-dev`, упомянутый в ранней версии журнала, не создаётся: предрелизные состояния тегами не помечаются.
